# Estado real de la base

Esta entrega conserva el código del prototipo como punto de partida, con documentación nueva basada en la definición. No es una implementación terminada de todo el producto. Fecha: 12 de noviembre de 2026.

| Área | Existe ahora | Pendiente para el producto |
|---|---|---|
| Interfaz | HTML/CSS/JS dinámico; acepta `#token=...`, usa Bearer y conserva el token en `sessionStorage` de la pestaña. Sin token muestra acceso bloqueado; demo es explícita. Se conserva el acceso manual de desarrollo. | Preparar/imprimir QR y programar NFC, modularizar JS, Radio Browser, imagen decorativa y pulido móvil. |
| Demo | Datos en localStorage, resultados y progreso identificados como simulados. | Audio/recursos de ejemplo publicables y completar el flujo final; las tareas de demo no continúan al cerrar la página. |
| API | Ocho operaciones; escrituras/importaciones requieren Bearer de al menos 32 caracteres validado por `FRAME_TOKEN_HASHES`. El primer `GET /state` autorizado crea el estado vacío persistente; accesos posteriores usan el mismo registro. `/media` devuelve URLs directas sin firma temporal. OpenAPI actualizado. | Radio Browser, imagen decorativa y otras funciones. |
| Identidad y lectura | Identificador fijo aleatorio por cuadro; SHA-256 deriva ámbito y rutas. Por decisión de Carlos, RTDB permite lectura sin sesión solo bajo `frames/{sha256}/slots`; Storage permite GET de objetos por URL conocida en `private/frames/{sha256}/`. No permite listar cuadros, leer tareas ni escribir. El cliente de ordenador usa únicamente el identificador y configuración pública RTDB/Storage; no hay Firebase Auth. Reglas aplicadas manualmente en Firebase real y comprobadas con lecturas públicas y rechazos. | Integración física en NFC/QR y portar el lector al firmware; leer medios reales importados. |
| Persistencia | RTDB bajo `frames/{sha256}` y SQLite local en filas separadas `frame_states`. El estado antiguo `prototypes/sonoro`/`state` no se migra. | Referencias a reproducciones activas, migración manual de datos antiguos destinados a un cuadro. |
| Tareas | Un worker dentro del proceso Uvicorn recorre los ámbitos; una importación activa por cuadro. | Recuperación fiable y exclusión/concurrencia entre procesos o réplicas; cancelación sigue parcialmente en memoria. |
| Medios | MP3 a 128 kbps, carátula 320×320 y nuevos objetos bajo `private/frames/{sha256}/{job_id}`. URLs directas descargables sin sesión ni caducidad firmada; la regla bloquea escrituras y listados. | Límites definitivos, normalización configurable, imagen decorativa y eliminación de recursos que ya no se usan. |
| Limpieza | Temporales de importación y algunas subidas fallidas se limpian. | Medios sustituidos, cancelaciones tardías y recursos huérfanos; no hay limpieza remota completa. |
| Emisoras | Nombre y URL HTTPS introducidos a mano. | Búsqueda Radio Browser y validación real de formato, acceso y compatibilidad web/ESP32. |
| ESP32 | Sin código funcional ni hardware elegido. | Streaming, pantalla, controles, persistencia local y portal Wi-Fi. |

Los límites de 15 minutos, 40 MiB y la carátula 320×320 son valores del prototipo, no decisiones definitivas de producto. No confundir flags de configuración de `/health` con permisos verificados. Las URLs de medios son legibles por cualquiera que las conozca; la ruta SHA-256 separa registros, no sirve de autorización. Las reglas actuales no se han desplegado a Firebase real.

La conexión local al proyecto Firebase real está configurada en archivos ignorados por Git. Se reutilizó el identificador aleatorio local existente para un cuadro de prueba, se guardó en `secrets/frame-test-token.txt` y se añadió su hash a `FRAME_TOKEN_HASHES`. Con la API local, `/state` devolvió 200 para ese identificador y 401 para uno no autorizado; el registro se limpió. Las reglas fueron aplicadas manualmente en Firebase Console. Con la API detenida, el cliente de ordenador leyó la configuración publicada y descargó un objeto de prueba sin credenciales ni sesión; listados, tareas y escrituras públicas fueron rechazados. El cuadro temporal y su prefijo de objetos quedaron vacíos tras la limpieza. La CLI sigue sin permisos para futuros despliegues. No se hicieron importaciones de YouTube; falta importar un medio real y escucharlo en la web, además de portar el lector al firmware y generar QR/programar NFC. Resultados detallados en [VALIDACION.md](VALIDACION.md).

Consultar [validaciones](VALIDACION.md), [plan](PLAN.md) y [definición](DEFINICION.md). No desplegar el prototipo actual como producto listo: falta validar Firebase real, firmware/hardware, integración QR/NFC y recuperación fiable de tareas.
