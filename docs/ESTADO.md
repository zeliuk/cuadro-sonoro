# Estado real de la base

Esta entrega conserva el código del prototipo como punto de partida, con documentación nueva basada en la definición. No es una implementación terminada de todo el producto. Fecha: 12 de noviembre de 2026.

| Área | Existe ahora | Pendiente para el producto |
|---|---|---|
| Interfaz | HTML/CSS/JS dinámico; acepta identificadores de 1–128 caracteres desde `#token=...`, los conserva en `sessionStorage` y limpia el fragmento. El ID solo selecciona ámbito; demo separada y explícita. | Preparar/imprimir QR y programar NFC, modularizar JS, Radio Browser, imagen decorativa y pulido móvil. |
| Demo | Datos en localStorage, resultados y progreso identificados como simulados. | Audio/recursos de ejemplo publicables y completar el flujo final; las tareas de demo no continúan al cerrar la página. |
| API | Ocho operaciones; el identificador Bearer selecciona un ámbito pero no autentica. IDs válidos de 1–128 caracteres crean o recuperan estado; no hay lista de acceso. SHA-256 común a API y cliente directo. `/media` devuelve URLs directas sin firma temporal. OpenAPI actualizado. | Radio Browser, imagen decorativa y otras funciones. |
| Identidad y lectura | Cualquier identificador válido crea o recupera un cuadro sin alta; SHA-256 deriva ámbito y rutas. Por decisión de Carlos, RTDB permite lectura sin sesión solo bajo `frames/{sha256}/slots`; Storage permite GET de objetos por URL conocida en `private/frames/{sha256}/`. No permite listar cuadros, leer tareas ni escribir. El cliente de ordenador usa únicamente el identificador y configuración pública RTDB/Storage; no hay Firebase Auth. Reglas aplicadas manualmente en Firebase real y comprobadas con lecturas públicas y rechazos. | Integración física en NFC/QR y portar el lector al firmware. |
| Persistencia | RTDB bajo `frames/{sha256}` y SQLite local en filas separadas `frame_states`. El estado antiguo `prototypes/sonoro`/`state` no se migra. | Referencias a reproducciones activas, migración manual de datos antiguos destinados a un cuadro. |
| Tareas | Un worker dentro del proceso Uvicorn recorre los ámbitos; una importación activa por cuadro. | Recuperación fiable y exclusión/concurrencia entre procesos o réplicas; cancelación sigue parcialmente en memoria. |
| Medios | MP3 a 128 kbps, carátula 320×320 y nuevos objetos bajo `private/frames/{sha256}/{job_id}`. URLs directas descargables sin sesión ni caducidad firmada; la regla bloquea escrituras y listados. | Límites definitivos, normalización configurable e imagen decorativa. |
| Limpieza | Al vaciar un hueco, reemplazarlo por una emisora/importación o iniciar la API se eliminan medios sin referencias, preservando selecciones y subidas activas. Los fallos se reintentan al próximo borrado o reinicio. Se comprobó en Firebase real que borrar un favorito eliminó audio e imagen. | El ESP32 aún no existe y no puede registrar reproducciones activas. |
| Emisoras | Nombre y URL HTTPS introducidos a mano. | Búsqueda Radio Browser y validación real de formato, acceso y compatibilidad web/ESP32. |
| ESP32 | Sin código funcional ni hardware elegido. | Streaming, pantalla, controles, persistencia local y portal Wi-Fi. |

Los límites de 15 minutos, 40 MiB y la carátula 320×320 son valores del prototipo, no decisiones definitivas de producto. No confundir flags de configuración de `/health` con permisos verificados. Las URLs de medios son legibles por cualquiera que las conozca; la ruta SHA-256 separa registros, no sirve de autorización. Las reglas actuales fueron aplicadas manualmente a Firebase real; no se utilizó Firebase CLI.

La conexión local al proyecto Firebase real y el identificador anterior del cuadro están en archivos ignorados por Git. Las reglas aplicadas manualmente permiten lectura directa de slots y medios por URL conocida; bloquean listados y escrituras públicas. El 12 de noviembre de 2026 se importó «Carefree» de Kevin MacLeod desde una búsqueda real de YouTube con Docker local. El MP3 y la portada se publicaron en Storage y se verificaron en RTDB público y API; después Carlos pidió borrarlos y se retiraron la selección, el audio y la imagen. Chrome Headless reprodujo el MP3 y avanzó sin errores antes de la eliminación; no se comprobó escucha humana. Compose queda ejecutándose localmente. Siguen pendientes Render, recuperación fiable, firmware/hardware y QR/NFC físicos. Resultados en [VALIDACION.md](VALIDACION.md).

Consultar [validaciones](VALIDACION.md), [plan](PLAN.md) y [definición](DEFINICION.md). No desplegar el prototipo actual como producto listo: falta Render, firmware/hardware, integración QR/NFC y recuperación fiable de tareas.
