# Instrucciones para el proyecto de ChatGPT «Cuadro sonoro»

Trabajamos en cuadro-sonoro, un cuadro decorativo musical con ESP32. Sonoro es el nombre provisional de la interfaz. El código se desarrolla con Codex en VS Code y se organiza en el repositorio público cuadro-sonoro.

Usa docs/DEFINICION.md (o su copia adjunta Definicion_cuadro_sonoro.md) como guía de producto y docs/ESTADO.md para distinguir lo implementado de lo previsto. Si una fuente está desactualizada o no está disponible, indícalo; no asumas acceso automático al código local, al repositorio o a los chats de Codex. Las decisiones nuevas del usuario actualizan la guía.


Web dinámica sin recargas, móvil primero y JavaScript modular sin framework. La web estática se alojará en `https://sonoro.zeliuk.xyz`; QR/NFC habitual abre `https://sonoro.zeliuk.xyz/#token=<id-cuadro>`. La web recibe el fragmento, lo conserva en sessionStorage y limpia la barra. El móvil necesita Internet, no la misma Wi-Fi que el cuadro. El ESP32 no sirve la web musical; su portal local separado configura Wi-Fi sin Internet, Render ni Firebase. En primera instalación crea una red temporal identificable por dispositivo y protegida por contraseña propia, muestra QR para conectarse e instrucciones; el portal cautivo ofrece una URL local de respaldo si no se abre. La contraseña doméstica solo se conserva en el ESP32. Distinguir conexión al router de acceso a Internet: una red sin Internet no equivale a contraseña incorrecta ni borra credenciales. Con credenciales guardadas, una caída de red no abre el asistente automáticamente. Después de configurar, el cuadro muestra el QR musical y el móvil debe volver a su red habitual. La API usa Python/FastAPI en `https://cuadro-sonoro.onrender.com`; yt-dlp busca y RapidAPI descarga el MP3 elegido. FFmpeg/ffprobe procesa medios; RTDB/Storage en Firebase; no Firebase Hosting. CORS debe permitir el origen exacto `https://sonoro.zeliuk.xyz` mediante `ALLOWED_ORIGINS`; no consta verificado en Render. Carlos comunica que el backend funciona en Render con RapidAPI; no es comprobación de Codex ni validación de hardware. El flujo integrado desde la web sigue pendiente. La búsqueda yt-dlp requiere runtime JavaScript compatible, yt-dlp-ejs y acceso a YouTube desde la máquina API. El identificador público del cuadro viaja como Bearer para seleccionar el ámbito, no autentica a nadie. Tiene entre 1 y 128 caracteres ASCII y API/cliente derivan el mismo SHA-256. No hay registro, Firebase Auth ni lista de IDs permitidos. Radio Browser para emisoras. Una importación por cuadro, progreso real, conservación de selección anterior ante fallos y limpieza de medios que ya no se usan, respetando reproducciones activas. El servidor Mac/Bonjour y los scripts locales se conservan únicamente como herramientas de desarrollo; no son acceso de producción. No se necesita servidor doméstico ni Raspberry Pi por cuadro. El ESP32 reproduce MP3 directamente desde Storage y emisoras desde sus streams; no hay órdenes remotas desde la web y la rueda física solo modifica su volumen. Distinguir selección publicada en Firebase del estado real de reproducción. Hosting HTTPS, CORS desde su origen y recorrido integrado aún requieren verificación. Los componentes del primer prototipo están seleccionados; cableado, alimentación, montaje y validación física siguen pendientes. Decisiones aprobadas de firmware: ESP-IDF 5.5.5, BSP Waveshare 2.0.0, LVGL 9.5.0 compartido, C++17, simulador SDL2 2.32.10 (CMake descarga SDL2/LVGL fijados), VS Code/Codex y transferencia inicial por USB; OTA queda para futuro. `firmware/common/` comparte vistas y recursos; `firmware/simulator/` conserva SDL2 y Firebase; `firmware/esp32/` contiene un modo diagnóstico v0.1 que no equivale al comportamiento producto. Wi-Fi, audio, portal, Firebase en placa y periféricos externos siguen sin implementar. Consultar `docs/HARDWARE.md` para la única lista de materiales y esquema de conexiones vigente y `firmware/README.md` para construir/transferir.

La vista opcional `/tablet/` muestra solo el cuadro virtual, sin el marco de la foto: dibuja un fondo cálido y una pantalla centrada que se adapta a la ventana, con imágenes independientes para los tres pulsadores y la rueda de volumen. Reutiliza la lógica de `/maqueta` para consultar selecciones, audio local y controles simulados. No controla el ESP32 ni modifica la configuración.

La primera demo visual de escritorio está en `firmware/simulator/`: C++/LVGL 9.5.0/SDL2, vista separada del teclado y SDL, recursos locales y canción simulada. También tiene un modo opcional que mantiene un flujo SSE abierto a RTDB, descarga las portadas de Storage y obtiene los `favicon` HTTPS de radios directamente de sus hosts, sin pasar por Render; al detectar cambios vuelve a preparar los medios y reinicia la ventana SDL. Las teclas `1`–`3` cambian entre los tres huecos y no descargan audio. Si los tres están vacíos, muestra el QR persistente; publicar contenido lo retira y vaciar todos los huecos lo vuelve a mostrar. Tocar un hueco vacío con contenido parcial muestra el QR 20 s y vuelve al estado visual previo. El lector usa un script Python y aún no está portado a C++/ESP32. El firmware ESP-IDF de diagnóstico está ahora en `firmware/esp32/`; no incluye audio real ni portal. `firmware/README.md` contiene instalación, ejecución y límites. El código compiló en macOS Intel; el modo Firebase aún requiere prueba con el identificador elegido y la demo falta comprobarla en Apple Silicon/M2 y escanear el QR con cámara.

Conservar la estética aprobada. Trabajar por fases pequeñas y explicar con claridad. No reabrir decisiones ya tomadas sin un problema concreto. Mantener comandos completos, carpeta de ejecución, ejemplos de endpoints, respuestas y errores. Distinguir mocks, servicios reales y hardware real. No pedir ni mostrar secretos ni activar facturación por iniciativa propia.

Los mensajes de commit usan un prefijo de tipo seguido de dos puntos, al estilo Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:` o `chore:`. El prefijo describe el cambio principal.

Estado: la API crea o recupera cuadros desde cualquier identificador válido; SHA-256 estable mantiene las rutas de datos y medios existentes. La web recibe `#token=...`, conserva el valor en `sessionStorage` de la pestaña y elimina el fragmento. Los QR del producto se generan con `scripts/generate_public_qr.py` y contienen `https://sonoro.zeliuk.xyz/#token=<id>`. El generador local Bonjour es una herramienta de desarrollo separada. Los PNG de cada ID son artefactos privados ignorados por Git. QR/NFC físico del cuadro siguen pendientes. Decisión de Carlos: la configuración publicada y los medios son legibles públicamente por URL conocida; las reglas bloquean listados y escrituras directas. Como el identificador no autentica, cualquiera que lo use puede cambiar ese ámbito mediante API. Admin SDK queda en backend/herramientas privadas. La primera importación real se publicó y avanzó en Chrome Headless; sigue pendiente la escucha humana y llevar el lector al firmware. Carlos comunica que el backend funciona en Render con RapidAPI; Codex no ha verificado el servicio remoto ni importaciones en esta fase y no se han aportado métricas o resultados detallados. Guía: `docs/PRUEBA_RAPIDAPI.md`. No se migran datos antiguos de la colección común. Para hardware del primer prototipo, consultar `docs/HARDWARE.md`: la selección de componentes y el esquema son documentales; ninguna pieza o conexión está validada físicamente todavía.
