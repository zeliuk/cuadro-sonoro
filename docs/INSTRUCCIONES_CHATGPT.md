# Instrucciones para el proyecto de ChatGPT «Cuadro sonoro»

Trabajamos en cuadro-sonoro, un cuadro decorativo musical con ESP32. Sonoro es el nombre provisional de la interfaz. El código se desarrolla con Codex en VS Code y se organiza en el repositorio público cuadro-sonoro.

Usa docs/DEFINICION.md (o su copia adjunta Definicion_cuadro_sonoro.md) como guía de producto y docs/ESTADO.md para distinguir lo implementado de lo previsto. Si una fuente está desactualizada o no está disponible, indícalo; no asumas acceso automático al código local, al repositorio o a los chats de Codex. Las decisiones nuevas del usuario actualizan la guía.

Decisiones: tres huecos con canción o emisora; un identificador por cuadro, sin registro; cualquier ID válido crea/recupera sus datos y no autentica a nadie; QR/NFC para configurar; tres pulsadores retroiluminados y rueda física; pulsar el activo detiene; pulsación larga restablece solo Wi-Fi con asistente local y QR. Arranque en silencio; una canción termina y se detiene. Sin SD, audio por streaming Wi-Fi y búfer. Imagen decorativa elegida en web, optimizada por servidor. La web configura y permite escuchar en el navegador, sin controlar remotamente sonido o volumen del cuadro.

Web dinámica sin recargas, móvil primero y JavaScript modular sin framework. El enlace usa `http://cuadro-sonoro-<id-dispositivo>.local/#token=<id-cuadro>`; hostname estable (independiente de IP) y token son identificadores distintos. La fase previa a firmware incluye servidor estático Python y Bonjour desde Mac, con QR local; el ESP32 servirá la web cuando se implemente. La web llama a la API Python/FastAPI con yt-dlp, FFmpeg y procesamiento de imágenes en Render/Docker; RTDB/Storage en Firebase; no Firebase Hosting. El identificador público del cuadro viaja como Bearer para seleccionar el ámbito, no autentica a nadie. Tiene entre 1 y 128 caracteres ASCII y API/cliente derivan el mismo SHA-256. No hay registro, Firebase Auth ni lista de IDs permitidos. YouTube con selección de resultado; Radio Browser para emisoras. Una importación por cuadro, progreso real, conservación de selección anterior ante fallos y limpieza de medios que ya no se usan, respetando reproducciones activas. El entorno de prueba Mac está implementado; la red y resolución deben verificarse desde el móvil del usuario. El servidor del ESP32 y la compatibilidad de móviles/routers aún deben implementarse/validarse en hardware.

Conservar la estética aprobada. Trabajar por fases pequeñas y explicar con claridad. No reabrir decisiones ya tomadas sin un problema concreto. Mantener comandos completos, carpeta de ejecución, ejemplos de endpoints, respuestas y errores. Distinguir mocks, servicios reales y hardware real. No pedir ni mostrar secretos ni activar facturación por iniciativa propia.

Los mensajes de commit usan un prefijo de tipo seguido de dos puntos, al estilo Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:` o `chore:`. El prefijo describe el cambio principal.

Estado: la API crea o recupera cuadros desde cualquier identificador válido; SHA-256 estable mantiene las rutas de datos y medios existentes. La web recibe `#token=...`, conserva el valor en `sessionStorage` de la pestaña y elimina el fragmento. El QR local ficticio se genera con `scripts/generate_local_qr.py`; QR del cuadro real y programación NFC siguen pendientes. Decisión de Carlos: la configuración publicada y los medios son legibles públicamente por URL conocida; las reglas bloquean listados y escrituras directas. Como el identificador no autentica, cualquiera que lo use puede cambiar ese ámbito mediante API. Admin SDK queda en backend/herramientas privadas. La primera importación real se publicó y avanzó en Chrome Headless; sigue pendiente la escucha humana y llevar el lector al firmware. Render y recuperación fiable de tareas no se han validado. No se migran datos antiguos de la colección común.
