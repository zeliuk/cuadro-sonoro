# Instrucciones para el proyecto de ChatGPT «Cuadro sonoro»

Trabajamos en cuadro-sonoro, un cuadro decorativo musical con ESP32. Sonoro es el nombre provisional de la interfaz. El código se desarrolla con Codex en VS Code y se organiza en el repositorio público cuadro-sonoro.

Usa docs/DEFINICION.md (o su copia adjunta Definicion_cuadro_sonoro.md) como guía de producto y docs/ESTADO.md para distinguir lo implementado de lo previsto. Si una fuente está desactualizada o no está disponible, indícalo; no asumas acceso automático al código local, al repositorio o a los chats de Codex. Las decisiones nuevas del usuario actualizan la guía.

Decisiones: tres huecos con canción o emisora; un identificador por cuadro, sin registro; cualquier ID válido crea/recupera sus datos y no autentica a nadie; QR/NFC para configurar; tres pulsadores retroiluminados y rueda física; pulsar el activo detiene; pulsación larga restablece solo Wi-Fi con asistente local y QR. Arranque en silencio; una canción termina y se detiene. Sin SD, audio por streaming Wi-Fi y búfer. Imagen decorativa elegida en web, optimizada por servidor. La web configura y permite escuchar en el navegador, sin controlar remotamente sonido o volumen del cuadro.

Web dinámica sin recargas, móvil primero y JavaScript modular sin framework. La web estática se alojará en `https://sonoro.zeliuk.xyz`; QR/NFC habitual abre `https://sonoro.zeliuk.xyz/#token=<id-cuadro>`. La web recibe el fragmento, lo conserva en sessionStorage y limpia la barra. El móvil necesita Internet, no la misma Wi-Fi que el cuadro. El ESP32 no sirve la web musical; tiene portal local independiente para configurar/restablecer Wi-Fi, cuya contraseña permanece en el dispositivo. La API usa Python/FastAPI en `https://cuadro-sonoro.onrender.com`; yt-dlp busca y RapidAPI descarga el MP3 elegido. FFmpeg/ffprobe procesa medios; RTDB/Storage en Firebase; no Firebase Hosting. CORS debe permitir el origen exacto `https://sonoro.zeliuk.xyz` mediante `ALLOWED_ORIGINS`; no consta verificado en Render. Carlos comunica que el backend funciona en Render con RapidAPI; no es comprobación de Codex ni validación de hardware. El flujo integrado desde la web y el hardware siguen pendientes. La búsqueda yt-dlp requiere runtime JavaScript compatible, yt-dlp-ejs y acceso a YouTube desde la máquina API. El identificador público del cuadro viaja como Bearer para seleccionar el ámbito, no autentica a nadie. Tiene entre 1 y 128 caracteres ASCII y API/cliente derivan el mismo SHA-256. No hay registro, Firebase Auth ni lista de IDs permitidos. Radio Browser para emisoras. Una importación por cuadro, progreso real, conservación de selección anterior ante fallos y limpieza de medios que ya no se usan, respetando reproducciones activas. El servidor Mac/Bonjour y los scripts locales se conservan únicamente como herramientas de desarrollo; no son acceso de producción. No se necesita servidor doméstico ni Raspberry Pi por cuadro. El ESP32 reproduce MP3 directamente desde Storage y emisoras desde sus streams; no hay órdenes remotas desde la web y el volumen físico usa la rueda. Distinguir selección publicada en Firebase del estado real de reproducción. Hosting HTTPS, CORS desde su origen y recorrido integrado aún requieren verificación; hardware y firmware siguen pendientes.

Conservar la estética aprobada. Trabajar por fases pequeñas y explicar con claridad. No reabrir decisiones ya tomadas sin un problema concreto. Mantener comandos completos, carpeta de ejecución, ejemplos de endpoints, respuestas y errores. Distinguir mocks, servicios reales y hardware real. No pedir ni mostrar secretos ni activar facturación por iniciativa propia.

Los mensajes de commit usan un prefijo de tipo seguido de dos puntos, al estilo Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:` o `chore:`. El prefijo describe el cambio principal.

Estado: la API crea o recupera cuadros desde cualquier identificador válido; SHA-256 estable mantiene las rutas de datos y medios existentes. La web recibe `#token=...`, conserva el valor en `sessionStorage` de la pestaña y elimina el fragmento. Los QR del producto se generan con `scripts/generate_public_qr.py` y contienen `https://sonoro.zeliuk.xyz/#token=<id>`. El generador local Bonjour es una herramienta de desarrollo separada. Los PNG de cada ID son artefactos privados ignorados por Git. QR/NFC físico del cuadro siguen pendientes. Decisión de Carlos: la configuración publicada y los medios son legibles públicamente por URL conocida; las reglas bloquean listados y escrituras directas. Como el identificador no autentica, cualquiera que lo use puede cambiar ese ámbito mediante API. Admin SDK queda en backend/herramientas privadas. La primera importación real se publicó y avanzó en Chrome Headless; sigue pendiente la escucha humana y llevar el lector al firmware. Carlos comunica que el backend funciona en Render con RapidAPI; Codex no ha verificado el servicio remoto ni importaciones en esta fase y no se han aportado métricas o resultados detallados. Guía: `docs/PRUEBA_RAPIDAPI.md`. No se migran datos antiguos de la colección común.
